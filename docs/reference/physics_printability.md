## 2. Per-formula physics check

### Tip-fuse sizing (`placement.tip_radius_mm`, `cco._r_tension_mm`)
- **Law encoded**: simple axial tensile design equation, σ = F/(πr²) ≤ σ_tensile/SF, solved for r.
- **Dimensional check**: F[N] · SF[–] / (π · tensile[Pa=N/m²]) → N/(N/m²) = m². √ → m. **Consistent.**
- **What "SF 8" is a safety factor of**: the ratio of the tip's green-state tensile strength to the design (peel-load) axial stress the tip is sized to carry — i.e. `actual_stress = tensile_green_mpa / 8` at design load. This is a classic strength safety factor, *not* an intentional-weak-link margin — the "fuse" language in design.md (design.md:29-30, "TIP is the fuse") refers to the tip being the **thinnest cross-section in the whole tree** (clamped to 0.2–1.0mm, §config.py:36-40) and hence the first thing a human snaps by hand during **post-cure** removal, when the resin is 4–6× stronger than the green state this SF is computed against (design.md:27: green ~10-25MPa vs post-cure ~40-60MPa). SF=8 is there to keep the tip from failing **in the print**, not to make it deliberately weak — its "weakest link at removal time" property comes for free from being the smallest clamped radius in the tree, not from the safety factor itself.
- **Oversimplification**: single scalar `peel_pressure_pa` (assumed 3000 Pa flat) stands in for a genuinely local, geometry-dependent peel stress; no dependence on separation speed, resin viscosity, or vat area at that layer — all real drivers of actual MSLA peel force. This is explicitly acknowledged as rough in the code.

### Deflection/stiffness solve (`placement._shaft_r_for_L`, `max_unbraced_len_mm`)
- **Law encoded**: cantilever point-load beam deflection, δ = 4FL³/(3EI), I = πr⁴/4 for a circular cross-section, solved for r (or inverted for L).
- **Dimensional check**: r⁴ = 4FL³/(3Eπδ). Units: N·m³ / [(N/m²)·m] = N·m³/(N·m⁻¹) = m⁴. **Consistent.** Inverse form (`max_unbraced_len_mm`) also checks out (verified independently in this audit): L³ = r⁴·3Eπδ/(4F) → m⁴·(N/m²)·m / N = m⁴·(N/m)/N = m⁴/m = m³. **Consistent.**
- Not strictly a "printability" formula (it's a structural/stiffness dimension) but it feeds `min(r0,r1) ≥ min_shoot_r_mm` gating in the printability angle-family switch, so it's included for completeness. This is out of this audit's primary remit; flagged for the sizing/structural auditor if not already covered.

### Per-segment printability rule (`tree.printability_report`)
- **Law encoded**: worst-case unsupported rim overhang per unit build height for a rotationally-symmetric (frustum) member: `max(0, drift + taper) ≤ tan(θ_max)`, where `drift = |Δc_xy|/dz` (lateral centroid drift rate) and `taper = (r_top−r_bot)/dz` (signed radius growth rate).
- **Dimensional check**: both `drift` and `taper` are mm/mm (dimensionless slopes); `tan(θ_max)` is dimensionless. **Consistent.**
- **Is it physically sound?** For a circular cross-section, the worst-case overhang direction is exactly the drift direction, and at that point the top disk's edge extends `r_top` while sitting `dz·drift` off-center of the bottom disk's edge at radius `r_bot` — so the true worst-case per-layer overhang is `dz·drift + r_top − r_bot = dz·(drift+taper)`, exactly what's coded. This is a correct refinement of the coarser discretized form the charter also quotes (`max(0,|Δc_xy|+r_up−r_low)`, design-v4.md:106-111) and rotational symmetry (frustum members) makes the refinement exact, not approximate. **No physics error found in this formula itself.**
- **What it does NOT encode**: it is a pure *rim-coverage/kinematic* rule. It never references `tensile_green_mpa`, `peel_pressure_pa`, or any adhesion/strength number — i.e. it treats "printable" purely as a resolution/geometry question, not an adhesion-strength question (whether the overhanging rim's bond to the layer below survives the next peel cycle). The charter itself frames θ_max as governed partly by "green-state bending... unsupported moment arm" (config.py:152-164) but that mechanical failure mode is never actually computed anywhere — θ_max is a flat empirical angle, not derived from any bending-stress-vs-tensile check. This is a genuine physics gap if the true failure mode is adhesion/bending rather than resolution (see §4, P3).

### `r_bend` (design-v4.md §6, curved-span eccentricity term)
- **Law encoded (per charter, not implemented)**: combined bending+axial stress on a curved span under peel tension T with centroid offset e from its chord: σ = T/(πr²) + 4Te/(πr³) ≤ tensile_green/SF, solved for r.
- **Dimensional check (on paper)**: 4Te/(πr³) → N·m/m³ = N/m² = Pa. **Consistent** if it were implemented.
- **Status**: grep across the whole `support_placement` package finds **no function that computes `r_bend`** — the only occurrence of the string is the docstring in `transient.py:520` quoting the charter's requirement. Per design-v4.md §14 (Phase plan, step 5) and §15, curvature/`r_bend`/curved-path transient arms are an **explicitly unimplemented future phase** ("Phase 5... Attack the unrouted/minima residual", design-v4.md:518-520). Consistent with the authoritative run numbers: no curved-member kind exists in the reported breakdown (stub/trunk/shoot/strut/brace/model_rung only), so all emitted members in the audited run are straight frustum chains and this gap does not affect the current run's correctness. **Flagged for future-phase tracking, not a live bug** in the audited results.

## 3. Resin-sensitivity ranking (evaluate against real ABS-like water-washable data)

Ranked by how much a shift in real resin data would change the engine's printability-relevant conclusions:

1. **`peel_pressure_pa` = 3000 Pa (assumed, "geometric mean of a plausible 1–5 kPa range")** — config.py:18-23. This single number scales `F` linearly, and every load-floored radius (`tip_radius_mm`, `_r_tension_mm`, the angle-aware term in `_shaft_r_for_L`) scales as `r ∝ sqrt(F)` (tip/tension floors) or `r ∝ F^{1/4}` (deflection floor). If real peel pressure for a water-washable ABS-like resin differs from 3 kPa by 2×, tip/tension-floored radii move ~40%, deflection-floored radii move ~19%. **This is the single largest lever in the whole printability/sizing chain and is explicitly self-flagged as unmeasured** (config.py `notes()`, line 409-413). It is process-dependent (lift speed, vat geometry) as much as resin-dependent, so "real resin data" alone may not resolve it.
2. **`tensile_green_mpa` = 10 MPa (assumed low end of a 10–25 MPa design.md range)** — config.py:25-29. Tip and Murray-floor radii scale as `r ∝ 1/sqrt(tensile)`. If the real water-washable ABS-like resin's **green** (uncured) tensile is materially below 10 MPa (plausible — the task's 30-50 MPa figure is *post-cured*; green is "much lower," and some fast/flexible-tough water-washable formulations report green tensile well under 10 MPa), every tip/tension-floored member is undersized relative to the design margin, i.e. genuinely thinner than SF=8 intends — the failure mode would show up as tip snapping *during* the print, not at removal. Conversely if real green tensile is *above* 10 MPa, all such members are over-margined (safe but wasteful of the "cost per length ∝ r²" objective — see charter §1). Only affects members NOT already floored by `min_shoot_r_mm`/`min_trunk_r_mm` (i.e., undersized/oversized risk is concentrated in fatter, load-carrying trunks/shoots, not the many members already sitting at the 0.35mm policy floor).
3. **`modulus_green_gpa` = 0.5 GPa (assumed low end of 0.5–1.5 GPa)** — affects only `_shaft_r_for_L`/deflection-floored members (`r ∝ E^{-1/4}`), a weaker exponent than tensile; lower real-world impact than #1/#2 but same directional sensitivity (softer green resin ⇒ current sizing under-conservative for stiffness).
4. **Resin *density*** — no config constant exists anywhere for it (confirmed by grep across `config.py` and the whole package: only "density" hits are about *support spacing density*, never mass density). The task's 1.05–1.2 g/mL range would let a mass-based cost/consumption check exist, but **the printability dimension currently has no mass-based check to be sensitive to** — this affects the volume-accounting/ChituBox-discrepancy investigation (a different dimension) far more than printability per se. Flagged here only because density's *absence* is itself the finding: any real-density number supplied by the parallel web team cannot currently move any printability conclusion, because nothing in this dimension consumes it.
5. **Resin *viscosity*** — likewise absent as a named constant; `shaft_drag_force_n` (0.01 N, flat, assumed) is the closest stand-in and is explicitly self-flagged as an order-of-magnitude guess. A real viscosity figure would let this be derived (e.g. via a Stokes-drag-style relation) rather than guessed, which would change every deflection-floored (`r_transient`, `r_deflect`) radius, but — same caveat as #1 — it is a *process* number (lift speed × viscosity) more than a resin-alone number.
6. **Post-cure tensile (30–50 MPa) is largely irrelevant to this dimension** — every printability/sizing formula in this codebase explicitly and consistently uses *green*-state tensile/modulus (design.md:27, config.py:25-29 comments), matching the physical reality that supports are stressed and printed while still green. Real post-cure numbers would only matter for the (unmodeled here) hand-removal snap force, which this audit's assigned files do not compute at all — see removal.py (`grip_handle_r_mm` etc., config.py:370-389) which is a different, already-self-flagged-soft dimension.

## 4. Suspected issues

**P1 — No explicit XY pixel-pitch / printer-resolution config constant; the only place printer resolution is used is a comment-only magic number.** *Severity: medium.* File: joints.py:69-77 (the only occurrence of an XY-resolution claim in the whole package — confirmed by grepping `pixel|dpi|xy_res|lcd|resolution` across `config.py`, `tree.py`, `joints.py`, `placement.py`). `layer_height_mm` (config.py:346) IS tied to a real printer profile ("Saturn 4 Ultra @ 50um"), but the comment's claim that "XY pixel pitch... sits around there [0.05mm]" is **not** similarly sourced to the Saturn 4 Ultra's actual display resolution/build-plate size — it is presented as a generic mSLA fact, and nothing in the code ever computes or checks a member's XY footprint against any pixel-pitch value (there is no `min_printable_r_mm` or `xy_pixel_mm` gate anywhere; `min_shoot_r_mm`=0.35mm and `tip_r_min_mm`=0.2mm are both justified purely as removal/mechanical-handling floors, not resolution floors — config.py:36-38, "a hobbyist-handling constraint, not a physics one; do not derive it"). **Confirm by**: pull the actual Saturn 4 Ultra XY pixel pitch from its spec sheet (mono LCD resolution ÷ build-plate X/Y) and compare against the assumed 0.05mm; if the real value is finer (many 12K mSLA panels are 0.015–0.03mm), `ENCLOSURE_TOL_MM` (joints.py:68, 0.02mm) is not automatically wrong but its justification ("well under half the feature scale") would need re-deriving from the real number, and there remains no formability check anywhere that would catch a genuinely too-thin feature on a *coarser* printer.

**P2 — Builder-side and verify-side printability checks use different formulas (chord-lean angle vs. rim-overhang drift+taper), with no taper term on the builder side.** *Severity: low (currently masked by verify passing clean).* Builder: `cco._within_cone`/`_lean_deg` (cco.py:88-110) checks only the straight-line chord angle `atan2(horizontal, |dz|)` against θ_max, with **no `taper` term at all** — a member's r0/r1 don't enter except in choosing which θ_max bucket applies. Verify (the actual gate, tree.py:558-589, wired at verify.py:460) checks `drift+taper` against `tan(θ_max)`. For a member whose radius stays constant at insertion time (r0==r1, taper=0) these coincide exactly. But `resize_forest` (transient.py, e.g. line 507-509) can subsequently fatten a "tapered pass-through" member's r1 relative to r0 (a real, load-driven Murray/transient fattening pass) *after* the builder's one-time accept check — at that point only the final verify-side gate (which does include the taper term) is checking correctness; the builder's tight `1e-6` tolerance comment (cco.py:103-109, "a verify gate must never be weaker than the thing that's supposed to satisfy it") is explicitly reasoning about the *builder* being no more permissive than verify, but does not itself validate that the builder's formula is the *same shape* as verify's, just that it's tighter on the terms it does check. In the audited run, `printability_violations` = 0 (given hard-gate summary), so this has not manifested as a live defect, but it is a latent inconsistency the next resize/rewire change could expose silently, since nothing tests that the two formulas agree on a genuinely tapered accepted member. **Confirm by**: construct a fixture where a straight member is accepted with r0==r1 at insertion, then resized to r1 > r0 by enough that `taper` alone (with drift already near the cone boundary) would push `drift+taper` over `tan(θ_max)` while the chord-only `_lean_deg` stays comfortably inside; check whether the resize path re-invokes any builder-side or only the final global verify gate (and whether the final gate would actually be exercised before shipping, vs. only being computed for reporting).

**P3 — The overhang/angle limits (`max_segment_angle_deg`=45°, `branch_angle_deg`=60°) are pure geometric/resolution rules; the mechanical failure mode the charter itself invokes to justify them (green-state bending under peel, config.py:157-159) is never actually computed.** *Severity: medium.* config.py:152-165 explicitly cites two justifications for the 45° default: (a) layer continuity/resolution and (b) "green-state bending of the inclined member under peel (unsupported moment arm grows with tan(theta))." Only (a) is encoded (the drift+taper geometric rule in tree.py). (b) — an actual bending-stress-vs-tensile check for inclined members — is not computed anywhere in the printability path (it *is* partially present in the unrelated angle-aware **deflection/stiffness** solve, `_shaft_r_for_L`'s `tan_t` term, placement.py:135-153, but that sizes for a fixed *deflection budget*, not a *strength* limit, and is a different config knob entirely). This means θ_max is doing double duty as both a resolution limit and a strength limit without the strength side ever being checked quantitatively — the 45°/60° split is corpus-evidenced (227 model-adsorbed struts) rather than physics-derived for the strength claim, which the charter itself acknowledges (design-v4.md:118-128, "plausible physics... but is a CALIBRATION HOOK, not an assumption"). **Confirm by**: for a batch of accepted 55–60° members near the `min_shoot_r_mm` boundary, compute σ_bend from the inclined-moment-arm argument config.py already states in prose and check whether it's actually within `tensile_green_mpa/SF` at the modeled `peel_pressure_pa` — if it is not, the corpus's 227 successful prints are evidence the *assumed* peel_pressure/tensile combination is conservative enough in practice, not evidence the geometric-only check is sufficient in general.

**P4 — Two different "minimum member radius" floors (`min_shaft_r_mm`=0.3mm vs `min_shoot_r_mm`=0.35mm) coexist; the lower one is dead in practice for every load-bearing branch member.** *Severity: low (currently safe, but confusing/dead code risk).* `min_shaft_r_mm` (config.py:61) is applied as the absolute floor inside `_shaft_r_for_L`'s return (placement.py:153: `max(r_m * 1000.0, cfg.min_shaft_r_mm)`), but every caller that uses that result for an actual shoot/strut/trunk member additionally floors the *result* against `cfg.min_shoot_r_mm` (0.35mm) or `cfg.min_trunk_r_mm` (0.8mm) one level up (cco.py:344-345, 435, 438, 488, 582; rewire.py:164, 252, 340, 416, 614; transient.py:609). Since 0.35 > 0.3, `min_shaft_r_mm`'s floor never binds for these paths — the tighter downstream floor always wins. Not unsafe (the tighter constant is conservative), but it means `min_shaft_r_mm` is effectively vestigial for printability purposes and could silently diverge from `min_shoot_r_mm` in a future edit without any test catching it (no fixture appears to isolate `_shaft_r_for_L`'s raw, un-re-floored output). **Confirm by**: grep for any call site that consumes `_shaft_r_for_L`'s return value *without* an immediately subsequent `max(..., min_shoot_r_mm)` or `min_trunk_r_mm` floor; if found, that's the one path where the lower 0.3mm floor is live and worth auditing on its own.

**P5 — No resin density (g/mL) or viscosity constant exists anywhere in the codebase.** *Severity: informational for this dimension, likely higher severity for whatever dimension owns the ChituBox 9.99ml vs. our 12.84ml volume discrepancy.* Confirmed by grep across `config.py` and the full `support_placement` package: every "density" occurrence refers to support-spacing density (contacts/area), never mass density; `peel_pressure_pa`/`shaft_drag_force_n` are the only stand-ins for material/process properties and both are self-flagged rough estimates. This means no formula in the printability dimension can be validated or invalidated by a real density figure — that number is orthogonal to everything audited here (confirming this so the parallel resin-data team and the volume-accounting auditor don't expect this dimension's conclusions to move on density data). **Confirm by**: nothing to confirm within this dimension; this is a scope-boundary note, not a bug.

**P6 — Joint/junction tolerances (`COINCIDE_TOL_MM`=0.15mm, `ON_AXIS_TOL_MM`=0.2mm, `PLATE_BAND_MM`=0.2mm, `COLINEAR_*`) are pinned as absolute millimetre magic numbers, not expressed as a multiple of `layer_height_mm`, contrary to the charter's own explicit 2026-07-22 ruling.** *Severity: low today, will become correctness-relevant if layer height ever changes.* design-v4.md:413-436 states, as a binding principle: "any tolerance whose rationale is print resolution... must be expressed as a multiple of `cfg.layer_height_mm`, never as an absolute millimetre pinned to the current 0.05mm profile," and gives `minima_connect_layers` as the pattern every such tolerance should follow. `joints.py:51-60`'s clustering/collinearity tolerances are resolution-class tolerances (they exist to decide whether two endpoints are "the same point" at print scale) but are hardcoded absolute-mm magic numbers with no `_layers` naming or derivation from `cfg.layer_height_mm`. ## Answers to the specific questions posed

- **Minimum printable radius vs. layer height and XY pixel size**: the codebase's minimum radii (`tip_r_min_mm`=0.2mm, `min_shoot_r_mm`=0.35mm) are set for **removal-friendliness/mechanical-handling reasons only** (config.py:36-38 says so explicitly), not derived from or checked against either `layer_height_mm` (0.05mm, real Saturn 4 Ultra profile) or any XY pixel-pitch value. **No printer XY resolution is formally assumed anywhere except one unsourced comment (joints.py:69-70, ~0.05mm) used only to justify dropping redundant joint-balls from emission — it is never used to validate that any member radius is actually resolvable.** At the assumed ~0.05mm scale, both the 0.35mm strut floor (14 assumed-pixels across) and the audited run's max 1.334mm trunk radius are comfortably above any plausible minimum-feature threshold for mSLA — **formable at the stated (if unsourced) assumption** — but the engine currently has no code path that would catch a radius that *wasn't* formable, because no such gate exists (P1).
- **Overhang/angle limits on members**: `max_segment_angle_deg`=45° (default) / `branch_angle_deg`=60° (r ≥ 0.35mm) / `strut_fallback_max_angle_deg`=60° (model-anchored struts), all enforced via `tree.printability_report`'s `max(0,drift+taper) ≤ tan(θ_max)` rule (dimensionally consistent, geometrically correct for circular cross-sections). All three angle constants are corpus-evidenced empirical calibration hooks, not physics-derived — none depends on any resin property.
- **Tip-fuse SF 8, of what quantity**: safety factor on axial tensile stress vs. **green-state** tensile strength (`tensile_green_mpa`, assumed 10 MPa) at the peel-load-derived design force — i.e. `σ_design = tensile_green_mpa / 8`. Not an intentional weak-link margin; the tip's "fuse" behavior at removal time comes from being the smallest clamped radius in the tree (0.2–1.0mm band), not from SF itself.
- **Is the 0.35mm strut / 1.33mm trunk formable**: yes, at the assumed (but unverified/unsourced) ~0.05mm XY resolution both are well above any plausible minimum feature size; but the engine performs **no explicit formability check** against printer resolution for either, so "formable" is currently an assumption made in prose comments, never a computed/gated guarantee.
