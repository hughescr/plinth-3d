# FU-8g design — the initial-contact preflight bound, and the four call sites behind it

> **PROVENANCE.** Designed 2026-08-08 by a read-only design agent against the main checkout at
> `develop @ e3168c5` (E8, Python-free; gates 1041 == 1041; the seven frozen OD-8 census digests
> as named in the spawn brief). **Nothing in the repo was edited, committed or built** — `git
> status` was clean before and after. The measurement in §M is a **scratch estimate produced
> outside the repo**: a standalone dependency-free Rust program in `$TMPDIR` that parses the
> corpus binary STLs and replicates `geom_kernel`'s own `moller` predicate and `EPS`; it is
> **NOT** the measurement of record and **must not be quoted as a landed number**. The
> implementing phase re-measures in-process at its own base commit (the §14/§17 precedent:
> env-gated instrumentation, reverted by editing before the gates). All figures marked
> *(derived)* are arithmetic over source constants and are exact; all figures marked *(estimate)*
> are the scratch proxy; all figures marked *(prediction)* are predictions and are labelled as
> such throughout.

## VERDICT, IN ONE PARAGRAPH

`hits_per_ray = nfaces` is **an artifact, not an honest worst case** — and it is worse than the
brief supposed, in two independent ways. (1) It is not only a *charge*: the same number is the
**eager allocation capacity** of eight per-ray buffers and, through `samples_per_ray =
(nfaces + 1) × cap`, of four more, so the artifact reserves memory as well as refusing runs.
(2) The work-items wall at 232,585,208 is **the first of two**: repricing it alone moves the
refusal one line down in the same function to `resource: "scratch bytes"` at **≈6.42 × 10¹¹ B
(642 GB)** against `536,870,912` — a demand **6.4× above the 100 GB machine ceiling**, which no
cap raise can ever admit. The chosen lever is therefore **(c) + (a): a batch-first algorithmic
fix in `geom_kernel` — count the crossings before charging and before allocating — and reprice
every derived quantity from the counted number.** No cap is raised, lowered or touched; on the
scratch estimate the honest demand lands at **0.9 %–27 % of the unchanged 4,000,000 flat cap**
and **≈1.5 % of the unchanged 512 MiB scratch cap**. The fix belongs in the shared kernel
requirement function, not in `initial::preflight`, because the same artifact governs four other
call sites — including one (the contact attestation, inside the very function that refuses) that
would eagerly reserve **≈67 GB** of interval output the moment the preflight stops refusing, and
one (brace) whose production caps today admit **at most 85 rods** on this mesh *(derived)*.

## F3. What the stage is actually doing per (contact, face) — and it is not "per face" at all

The only consumer of the preflighted penetration budget in this stage is
`classify_initial_overlaps` (`initial.rs:875–916`): **one** batched
`penetration_intervals_batch_bounded` over all contact stubs (`:891–903`), then a per-seed
`remaining_illegal_axis_overlap` fold (`:906–913`). The stub geometry is built at
`initial.rs:494–508`:

```rust
let p0 = position - unit * contact_depth;   // :497   DEFAULT_CONTACT_DEPTH_MM = 0.3  (placeholders.rs:1099)
let p1 = position + unit * span;            // :498   STUB_LENGTH_MM         = 2.5  (placeholders.rs:1358)
```

so the queried ray is a **2.8 mm segment** straddling the seat, aimed outward along the contact
normal. With `rays_all = false`, `capsule_rays` (`queries.rs:80–108`) yields exactly **one** ray
(`offset_count = usize::from(rays_all && ...) * n_offset_rays`, `:90` — the `8` passed at
`initial.rs:394` is *inert* on this path).

Inside `pen_intervals_one` (`queries.rs:1529–1699`) the per-ray crossing set comes from
`collect_hits_with_stack` (`:1242–1282`), which is a **BVH traversal**: it pops nodes, rejects on
`ray_box`, and runs `moller` only on the triangles of leaves the segment's box actually reaches.
So the executed hit count is *geometry-bounded*, and the executed test count is
*traversal-bounded*. Nothing in the executed path is O(faces).

## F4. Where `nfaces` enters, and everything it poisons

`penetration_requirements`, `rust/geom_kernel/src/queries.rs:1701–1815`:

```rust
let hits_per_ray = self.mesh.nfaces();                                        // :1737
let subsegments_per_ray = hits_per_ray + 1;                                   // :1738
let samples_per_ray     = subsegments_per_ray * cap;                          // :1739
let intervals_per_row   = rays * subsegments_per_ray;                         // :1740–1741
let work_per_row        = rays * hits_per_ray;                                // :1742
...
work:      rows * work_per_row,        // :1801   ← the wall
hits:      rows * work_per_row,        // :1802   (work and hits are the SAME quantity)
samples:   rows * samples_per_row,     // :1803
intervals: rows * intervals_per_row,   // :1804
scratch:   rows * row_scratch,         // :1805
```

`row_scratch` (`:1753–1795`) sums **fourteen** buffers, of which eight are sized by
`hits_per_ray` or `subsegments_per_ray` and four by `samples_per_ray`. Every one of those sizes
is also the **actual reservation** in `pen_intervals_one` — `reserve_penetration_vec` is
`Vec::try_reserve_exact` (`queries.rs:550–565`), i.e. it allocates the capacity immediately:

- `hits`, `tvals`, `ts` at `budget.hits_per_ray` (`:1564`, `:1567`, `:1571`)
- `b_bounds` at `hits_per_ray + 2` (`:1574–1578`)
- `sample_pts`, `ins_all`, `dist_all` at `budget.samples_per_ray` (`:1583`, `:1610`, `:1613`)
- `slices`, `sub_bounds`, `insub`, `depsub` at `budget.subsegments_per_ray`
- `out` (the returned interval row) at `budget.intervals` (`:1548`) — **held for the whole batch**

**So this is not a paper bound.** `hits_per_ray = nfaces` is simultaneously the charge, the
refusal criterion, and the malloc size. That is what makes it an FU-8b-class defect rather than
an FU-8f-G5-class charging error — and it is why the fix must reach the allocation, not only the
charge.

## F8. `scratch_bytes = rows × row_scratch` is a second, independent over-statement

`penetration_intervals_batch_bounded` (`queries.rs:1896–1941`) is `par::run(|| (0..n)
.into_par_iter().map(|i| self.pen_intervals_one(...)).collect_into_vec(&mut per))`. Every buffer
sized by `row_scratch` is allocated **inside** `pen_intervals_one` and dropped when the closure
returns; the only per-row thing that survives is the interval output, which is charged
separately by `max_total_intervals` / `interval_output_bytes`. So the **peak** transient scratch
is `min(rows, threads) × row_scratch`, not `rows × row_scratch` — at `PLINTH_THREADS=4` that is
an over-statement of **135.5×** on this batch. `par` re-reads `PLINTH_THREADS` per call
(`rust/geom_kernel/src/par.rs:4`).

**Recommended disposition: record it, do not act on it in this follow-up.** Charging a byte
ceiling from a runtime pool size couples a resource plan to an environment variable, which is the
kind of coupling FU-8d part (3) exists to prevent. Keep the aggregate `Σ_rows row_scratch(h_r)` —
which, once `h_r` is honest, is ≈6.8 MB *(estimate)* and no longer needs the 135× refinement.
This is Open Question 3.

## F9. `work` and `hits` are literally the same expression today, and they should not be

`queries.rs:1801–1802` sets both `work` and `hits` to `rows * work_per_row`. But they measure
different things: `hits` bounds the **length of the `hits` vector** (a storage quantity, exactly
the crossing count), while `work` is checked as a **time/operation** budget by
`initial::preflight` and by `check_penetration_limits`. Under `hits_per_ray = nfaces` the two
coincide because `nfaces` happens to bound both. Once the bound becomes honest they diverge:
crossings are ~62/ray, traversal tests are ~1,967/ray *(estimate, §M)*. **Repricing `hits` to
crossings while leaving `work` at crossings would under-charge the traversal by ~30×** — a real
regression in charging honesty, in the direction the house forbids. The design therefore splits
them (D3).

## F10. The `samples_per_ray = (h+1) × cap` term has a *closed-form* honest bound that needs no extra measurement

`pen_intervals_one:1601` computes, per subsegment, `ns = cap.min(3usize.max((lsub /
majority_step_mm).trunc() as usize))`. Since `min(cap, max(3, x)) ≤ max(3, x) ≤ 3 + x` and
`Σ_subsegments lsub = seg`:

> `samples_per_ray ≤ min( cap × (h + 1),  3 × (h + 1) + seg / majority_step_mm )`

Both arguments are known at preflight from the counted `h` and the segment length. On the initial
stage (`seg ≈ 2.8 mm`, `step = 0.12`) the second argument governs: `3 × 63 + 24 = 213` against
`80 × 63 = 5,040` — a further **24×** honesty gain that costs one `min`. This is a real
derivation, not an approximation, and it is the reason the honest scratch lands in the single-MB
range rather than the tens of MB.

# M. MEASUREMENT *(scratch estimate — NOT the measurement of record)*

**Method.** A standalone `rustc -O` program in `$TMPDIR/fu8g/hits.rs`, no dependencies, outside
the repo. It parses each corpus binary STL, reconstructs each face's geometric normal and
centroid, builds the stage's own stub segment (`p0 = c − n × 0.3`, `p1 = c + n × 2.5`, per
`initial.rs:497–498` with the registered constants) and counts, per ray, both:

- **crossings** — `moller(p0, p1−p0, v0, e1, e2, 1.0)` transcribed verbatim from
  `rust/geom_kernel/src/moller.rs:13–30` with `EPS = 1e-6`, `DET_EPS` as written, no backface
  culling — i.e. exactly the predicate `collect_hits_with_stack` applies;
- **candidates** — triangles whose AABB overlaps the segment's AABB. This is a **loose upper
  bound** on the triangles a BVH leaf scan would test (it ignores the directional `ray_box`
  rejection and the tree's pruning), so the real traversal count is lower.

Seats are proxied by **downfacing faces** (`n_z < −0.2`), stride-sampled to ≤4,000 rays per
model; the "all faces" arm is also reported and agrees within 8 %.

**Three caveats, stated because they bound what may be concluded.** (1) The seat proxy is not the
contact set — real contacts are chosen at minima/overhang seats by the perception stage, a
subset. (2) There is no BVH here, so the candidate column over-counts. (3) Offset (rim) rays,
which the attestation batch uses, were not measured. **Every number below is an order-of-
magnitude input to the design, and the implementing phase must replace all of them.**

| model | faces | rays | crossings mean / p50 / p95 / p99.9 / max | candidates mean / p95 / max |
|---|---:|---:|---|---|
| `make_box` | 12 | 2 | 1.00 / 1 / 1 / 1 / **1** | 2.0 / 2 / 2 |
| `make_overhang_table` | 60 | 10 | 1.00 / 1 / 1 / 1 / **1** | 2.0 / 2 / 2 |

### M1. The corpus demands 1–4 crossings and is charged 12–4,760. The treant demands ~62 and is charged 429,120

The seven corpus models pass this preflight *only* because they are small: `make_box`'s charge is
`n × 16` where its true demand is `n × 1`. The over-statement ratio is `nfaces / mean_crossings`
— 12× on the box, 4,760× on the Sphere, **6,918× on the treant**. Nothing about the treant is
special except that `nfaces` finally exceeds a flat cap.

### M2. The treant's tail is real and must not be averaged away

`p95 = 317` and `max = 1,106` crossings: a 2.8 mm segment through the weeping foliage genuinely
crosses hundreds of thin leaf shells. This is why the design **counts per row** rather than
applying a per-model coefficient: a uniform per-row budget at the p99.9 would charge
`542 × 1,002 × 33 B/sample-ish ≈ 1.4 GB` of scratch and re-create a smaller version of the same
problem, while the per-row sum is ≈6.8 MB.

### M4. The one number that is not comfortable, named now

If `work` is charged as **traversal tests** (D3, and it should be), the treant lands at
≈1.07 M against the 4,000,000 floor — **26.7 %**, on a proxy that over-counts. That is fine, and
it is the honest reading. But the p99.9 arm (`542 × 21,492 ≈ 11.6 M`) would exceed the floor if
the contact set concentrated in the densest foliage. **The design does not pre-emptively scale
the cap for a case the measurement has not shown** (that would be inventing a coefficient from a
proxy). It specifies the contingency instead, with the derivation rule bound in advance: see D5.

# DECISIONS

## D1 — THE LEVER: (c) batch-first algorithmic fix + (a) reprice from the counted work. **No cap is touched.**

Justified against the three precedents:

- **FU-8b** scaled two caps by a *measured per-face coefficient* because the quantity being
  bounded was genuinely proportional to faces (a kNN batch really is `sources × queries`; a
  parity grid really does hold per-face references). **Here it is not**: the executed query
  touches the faces a 2.8 mm segment reaches, and the measured ratio to `nfaces` is 6,918:1.
  Scaling a cap by a coefficient derived from a fiction would ratify the fiction. **Declined as
  the primary lever**; retained as the *contingency* (D5) with a measured coefficient, exactly as
  FU-8b's own rule prescribes.
- **The kNN/grid caps** are the shape FU-8b produced (`max(floor, per_face × faces)`); same
  argument, same disposition.
- **FU-8f G5** repriced `rows × contacts × (owner_log + 4)` to what the CSR transpose really
  spends, and the stated demand fell 4.75 × 10⁹ against an untouched cap. **This is that, plus
  one thing G5 did not have to do**: G5's over-statement was a pure charge, so repricing sufficed.
  Here the same number is the allocation size (F4), so the bound cannot be repriced without the
  algorithm producing it. **Hence (c) then (a), in that order, in one phase.**
- **FU-8b's fix (a)/(b)/(c)** — replace the defective derivation, then state the honest demand —
  is the closest structural precedent, and this follows it.

## D2 — THE MECHANISM: count, charge, allocate. One new batched kernel pass.

New in `rust/geom_kernel/src/queries.rs`, beside `penetration_requirements`:

```rust
/// One crossing/traversal census per ray, batched. No per-hit storage: the
/// BVH walk is identical to `collect_hits_with_stack`, but it counts instead
/// of pushing, so it needs O(bvh.depth) memory and nothing else.
pub struct PenetrationRowCensus { pub crossings: usize, pub tests: usize, pub seg_mm: f64 }

pub fn penetration_census_batch(
    &self, p0s: &[V3], p1s: &[V3], r0s: &[f64], r1s: &[f64],
    n_offset_rays: usize, rays_all: bool,
) -> Result<Vec<PenetrationRowCensus>, PenetrationBatchError>;
```

- **Batch-first by construction**: one `par::run` index-parallel map over rows, the same shape as
  `penetration_intervals_batch_bounded` (`queries.rs:1903–1924`). No per-item entry point is
  added, and no caller loops.
- Per row it sums over that row's rays (1 or `n_offset_rays + 1`), so a row's census is the row's
  budget — the rim rays are counted, not extrapolated.
- **Its own charge is trivial and self-bounding**: the walk visits ≤ `2 × leaves` nodes with an
  `O(bvh.depth + 1)` stack, which is already the `traversal_stack` term
  (`queries.rs:1745`). It allocates nothing per hit.
- **Cost**: one extra BVH descent per ray. The descent is a small fraction of the row's work,
  which is dominated by `pv.inside` + `nearest_one_with_stack` **per sample**
  (`queries.rs:1616–1624`) — and the sample count is itself collapsing by ~24× under F10.
  *(Prediction: the stage gets faster, not slower. It is a prediction, and H6 measures it.)*

Then `penetration_requirements` gains a measured sibling:

```rust
fn penetration_requirements_from_census(
    &self, census: &[PenetrationRowCensus], cap: usize, majority_step_mm: f64, rays: usize,
) -> Result<PenetrationBatchRequirements, PenetrationBatchError>
```

with, per row `r`: `hits_r = crossings_r`, `subsegments_r = crossings_r + rays_r`,
`samples_r = min(cap × subsegments_r, 3 × subsegments_r + seg_r / majority_step_mm)` (F10),
`intervals_r = subsegments_r`, `work_r = tests_r` (D3), and **totals that are sums, not
`rows × max`**. `PenetrationRowBudget` is already a per-row parameter of `pen_intervals_one`
(`queries.rs:1546`, passed as `requirements.row` at `:1921`); it becomes a **`&[PenetrationRowBudget]`
indexed by row**. That is the whole surgery — the row budget type does not change shape.

**Count-drift is a typed refusal, never a silent regrow.** `reserve_penetration_vec` uses
`try_reserve_exact`, so a `push` beyond the reserve would *grow* the vector rather than refuse —
an unafforded allocation. `pen_intervals_one` therefore gains a hard check: if
`hits.len() > budget.hits_per_ray` (or samples/subsegments exceed their budgets), return
`PenetrationBatchError::CensusDrift { row, resource, counted, executed }`. The census walk and
the fill walk are the same traversal over the same immutable BVH with the same predicate, so
drift is impossible by construction and the check is a proof obligation, not a fallback — but the
count-before-charge-before-allocate ordering (§14.4's standing rule: *"any future phase that
fixes this must keep count-before-charge-before-allocate; the target is to make the count cheap,
never to skip it"*) is preserved exactly, and a future edit that breaks it fails loudly.

**The worst-case entry point stays.** `penetration_intervals_batch_worst_case_limits`
(`queries.rs:1867–1885`) is a public sizing helper with test callers; it is **not** deleted and
**not** changed. Production callers move to the census path. That keeps the diff honest about
what changed behaviour and what did not.

## D3 — `work` and `hits` are severed (F9)

- `hits` := Σ crossings — a storage bound, and exactly the `hits`/`tvals`/`ts` reservation.
- `work` := Σ traversal tests (nodes visited + triangles tested), which is what the ray loop
  actually executes.

This is the G3/G6c severance idiom (charged vs executed, both stated) applied to two quantities
that were accidentally aliased. It makes `work` **strictly more honest than today in both
directions**: it stops over-charging by ~218× *(estimate)* and it stops the repricing from
under-charging the traversal by ~30×.

# OPEN QUESTIONS, WITH RECOMMENDED ANSWERS

1. **Charge `work` as traversal tests or as crossings?** → **Traversal tests** (D3). Crossings
   alone under-charge the executed loop by ~30× *(estimate)* and would be a charging regression
   dressed as a repricing. The cost is that the treant lands at ~27 % of the floor instead of
   ~0.9 %, which is the honest number, and H0 will replace the proxy with the real BVH count.
2. **Two poison labels or three?** → **Three** (D6). The owner mandated two (guard 3 vs identity
   walk); the four "commit shape" sites are neither, and bucketing them into the identity walk
   would re-create the exact ambiguity the rider exists to remove, one failure mode later. If the
   owner prefers strictly two, fold `CommitShape` into `IdentityWalk` and say so in the label's
   doc comment — but say it, don't imply it.
3. **Charge scratch as `Σ_rows` or as `min(rows, threads) × max_row` (F8)?** → **`Σ_rows`.**
   Coupling a byte plan to `PLINTH_THREADS` makes a resource plan environment-dependent, which
   FU-8d part (3) is precisely about not doing. Once the per-row size is honest the aggregate is
   ≈8 MB and the 135× refinement buys nothing. Record the observation; do not spend it.
4. **Should the worst-case sizing helper be deleted?** → **No.** `penetration_intervals_batch_
   worst_case_limits` (`queries.rs:1867`) has test callers and is a legitimate sizing helper; its
   doc comment already says it is "not a production policy". Move production off it, leave it,
   and let the diff show exactly which call sites changed behaviour.
5. **Scale `max_work_items` by the FU-8b batch-product rule now?** → **No** (D5.3). The measured
   demand fits the unchanged floor. Adding scaling that no measurement requires is the same class
   of error as raising a cap. The rule, the unit (one contact, **not** one face) and the
   derivation `next_power_of_two(2 × observed)` are written down now so that *if* H6 crosses the
   floor, the response is mechanical rather than negotiated.
6. **Does the census pass make the stage slower?** → *(Prediction)* **No** — the extra BVH descent
   is small against the per-sample `inside` + `nearest_one` work, and the sample count itself
   falls ~24× under F10. But this is a prediction, three of the last four missed, and H6 measures
   it. If it *is* slower, the fallback is to fuse census and fill into one pass with a two-phase
   buffer — which trades the clean count-before-allocate ordering for speed and must therefore be
   an owner-ruled decision, not an implementer's.
7. **What about the 542 → attestation 67 GB reserve if H1 slips?** → It is **not** a separate
   follow-up and must not be spun out. It is the same defect at the same line
   (`queries.rs:1548`), and H1 fixes it in the same edit. Named here only so that a partial H1
   ("fix `initial::preflight` and ship") is recognisable as the wrong thing.
8. **Should H0 run before H1, given it costs 3 points and produces no code?** → **Yes.** Every
   number in this design is a proxy from outside the repo. H1's per-row budget arithmetic, H3's
   registered provenance and D5's contingency all want a real distribution, and H0 is the cheapest
   phase in the plan. The §14/§17 precedent for measurement-only phases is established and
   worked twice.
